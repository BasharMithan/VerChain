# What's new in release v0.4.0

Version 0.4.0 adds configurable runtime settings and document-based credential registration, and completes the project's transition from BCIV to VerChain.

## Highlights

### Credential document uploads

- `POST /register` now accepts multipart form data, including the holder and issuer fields and a credential document upload. The registration fields are `user.name`, `user.nationalNumber`, `user.phone`, `user.age`, `user.email`, `user.birth`, `credential.credentialID`, `issuer.name`, and `issuer.issuerID`; upload the file as `credential.document`.
- Uploads are checked against the configured maximum size and supported file formats. PDF uploads are also checked to ensure they contain valid PDF data. Empty, oversized, unsupported, and invalid PDF files are rejected.
- VerChain hashes the document contents together with the file extension and credential ID. The document itself and its original filename are not stored in the ledger; the ledger keeps the resulting digest and document metadata.
- `GET /credential-constraints` returns the node's maximum upload size and supported formats so clients can adapt to its upload policy.

### Centralized YAML configuration

- Runtime settings are loaded from `settings.yml` and validated with Pydantic. If the configuration file is missing, VerChain creates it with default settings.
- Configuration covers proof-of-work difficulty, the ledger's `SAFE` or `FAST` performance mode, bootstrap peers, and credential upload constraints.
- Defaults allow PDF uploads up to 5 MiB and use the local node at `127.0.0.1:8000` as the bootstrap peer.

### VerChain project identity

- The project and package have been renamed from BCIV (Blockchain-Based Identity Verification) to VerChain.
- Project-facing names were updated in package metadata, the node console, documentation, and development assets.

### More resilient startup and security reporting

- Ledger initialization now creates its parent storage directory when needed, making first-run setup more reliable when the configured storage path does not yet exist.
- A security policy documents private vulnerability reporting, responsible testing, and coordinated disclosure. This establishes a reporting process; it does not represent a claim that the release independently hardens every application component.

### Development and test workflow

- CI runs unit and functional tests on Python 3.11 and 3.12, runs real-socket integration tests in a separate job, and publishes a coverage report.
- Configuration loading and document registration—including upload constraints, invalid files, and multipart request handling—have dedicated test coverage.

## Migration note

Clients that previously sent JSON to `POST /register` must switch to `multipart/form-data` and send the credential file using the `credential.document` field. Use `GET /credential-constraints` to discover the node's current file-size and format limits.
