# What's New in Release 0.5.0

VerChain 0.5.0 refactors credential storage around uploaded documents. The release introduces a nested `Document` model, document upload validation and hashing, and updates the registration, verification, and ledger paths to use the new credential schema.

## Highlights

1. **Credential and document model**
   - Replaced the legacy flat identity/image representation with `Credential(document=Document(...), documentID=...)`.
   - `Document` carries the title, content, format, content size, and document hash. Byte content is encoded as base64 for JSON serialization.
   - A credential's `CID` is derived from its document hash and `documentID`.

2. **Document upload and validation**
   - Registration accepts a multipart file upload at `credential.document` and uses `credential.documentID` to identify the credential.
   - Uploads are checked against the configured maximum size and supported file formats. PDF uploads are also checked for a PDF signature.
   - Added `GET /credential-constraints` to expose the server's maximum upload size and supported formats.

3. **Document hashing**
   - Document hashes use SHA-256 over the uploaded bytes, normalized filename extension, and document ID, separated by colons:
     `SHA-256(content + ":" + extension + ":" + documentID)`.
   - Hashing the actual bytes avoids hashing a string representation of the content and binds the digest to its format and ID.

4. **Ledger, validation, and API updates**
   - Updated credential lookup, block registration, chain synchronization, and ledger loading to use `documentID` and the nested document schema.
   - Added specific errors for unsupported and oversized uploads, and report invalid ledger records as ledger corruption during loading.
   - Updated API models and documentation from the legacy identity terminology to credentials.
   - Expanded regression tests for API upload behavior, hashing, persistence, and chain synchronization.

## Upgrade Notes

- Registration and verification clients must use `documentID`; the multipart registration file field is `credential.document`.
- The persisted credential schema is not backward-compatible with ledger records using the old `image` and `credentialID` fields. Existing ledgers are not automatically migrated and should be backed up and migrated before upgrading.
- The current `Document` model includes uploaded content in serialized ledger blocks. Ledger files and backups should therefore be handled as sensitive data.
